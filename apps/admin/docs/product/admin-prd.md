# Kokoro Admin 产品需求

状态：产品范围冻结，尚未实现与验收。

## 1. 产品定位

Kokoro Admin 是独立部署的统一管理后台。首个版本覆盖身份、租户、访问控制、会话和审计，
帮助平台管理员在一个稳定、高密度且响应迅速的工作界面内完成重复管理任务。

Admin 是前端产品，不拥有 IAM 数据和业务规则。当前阶段不修改 `kokoro-iam`；Admin 通过版本化
API 契约独立开发，后续联调只替换契约数据来源，不改变页面结构和交互模型。

## 2. 产品原则

1. 以 `satnaing/shadcn-admin@e16c87f` 为视觉、布局和组件组织底座；shadcn/ui 原语仍由官方
   CLI 与 Registry 管理。
2. 使用 Next.js 16 App Router、Auth.js、shadcn/ui、Tailwind CSS 4、Radix UI、Lucide、
   TanStack Table、React Hook Form 和 Zod。
3. 后端领域规则、授权和数据归 IAM；页面、交互和显示状态归 Admin；双方只通过生成的
   ConnectRPC 契约协作。
4. 导航中只出现具有真实产品职责、明确 API、权限投影和验收用例的页面。
5. 只实现 Kokoro 的真实管理业务，不引入示例业务或示例数据。
6. 同一种管理任务只保留一套页面与组件实现。独立 Admin 和未来产品内管理入口仅改变入口、
   导航和数据范围，不复制业务组件。
7. 界面隐藏不是授权边界。前端按服务端返回的能力投影展示操作，IAM 仍对每个命令最终授权。
8. 上游 Tasks、Chats、Apps 等示例业务不进入生产导航，但其成熟的表格、Dialog、Sheet、表单、
   搜索、响应式和可访问性模式可以适配到 Kokoro 真实功能。

## 3. 用户与范围

| 用户 | 可见范围 | 行为 |
|---|---|---|
| 未登录用户 | 登录页 | 选择可用认证方式，完成认证或看到不泄露账户状态的失败反馈。 |
| 普通用户 | 无 Admin 范围 | 不显示管理入口；直接访问受保护路由得到明确的禁止访问页面。 |
| Site 管理员 | 当前 Site | 未来从产品侧进入时，仅看到当前 Site 及其成员和访问控制能力。 |
| 平台管理员 | 全局 | 使用独立 Admin 管理用户、组织、Site、角色权限、会话和审计。 |

平台超级管理员由 IAM 的初始化或维护脚本创建和重置密码。Admin 不提供公开管理员注册。
开发和测试账号工具必须显式开启，生产构建不可见且不可调用。

## 4. 产品范围

### 4.1 登录

- Auth.js 管理浏览器 Session、Cookie、CSRF、回调和安全重定向。
- 登录支持账号/邮箱加密码；邮件登录只在服务能力可用时展示。
- 注册不提供账号密码入口；开发测试账号由受环境开关保护的工具创建。
- 登录失败不向公开页面泄露账号是否存在、已停用、已删除或无管理权限。
- 认证成功后仍需服务端确认管理权限，不能以客户端状态替代。

### 4.2 Dashboard

- 展示来自权威 API 的用户、租户、活跃会话和安全事件摘要。
- 展示需要管理员处理的异常与最近活动，并提供到对应工作区的快捷入口。
- 不通过前端推断风险等级，不展示虚构指标、示例趋势或 Demo 数据。

### 4.3 用户

- 搜索、状态筛选、游标分页和列显示设置。
- 查看身份概览、组织/Site 关联、角色、会话和审计上下文。
- 执行停用、恢复、软删除、恢复删除以及撤销会话。
- 平台角色仅按契约允许的能力修改；所有危险操作要求确认和原因。

### 4.4 组织与成员

- 创建、搜索、筛选、查看、编辑、软删除和恢复 Organization。
- 在详情工作区管理成员的加入、角色变更、停用、恢复、移除和删除恢复。
- Organization 与 Site 是两个独立领域概念，不互为别名。
- Owner 连续性、跨范围访问和恢复冲突由 IAM 裁决，前端准确呈现错误码结果。

### 4.5 Site 与成员

- 创建、搜索、筛选、查看、编辑、暂停、恢复、软删除和恢复 Site。
- 在详情工作区管理成员生命周期、角色分配、权限结果和相关审计事件。
- Site 管理员的查询与命令始终绑定当前 Site；平台管理员才可切换全局范围。

### 4.6 角色与权限

- Organization 角色和 Site 角色使用同一 `RoleWorkspace` 交互模式，但保持不同数据范围。
- 角色列表与权限树采用主从布局，展示角色状态、成员使用量和权限分组。
- 自定义角色支持创建、编辑、权限集合保存、软删除和恢复。
- 内置角色只读；删除中的角色不能继续分配；恢复后重新进入可选范围。
- 权限目录、授权结果和成员影响均来自 API，不在前端重建权限闭包。

### 4.7 会话

- 按用户、状态、时间和客户端信息筛选会话，不展示原始 Session Token。
- 支持撤销单个会话和按契约允许的范围撤销全部会话。
- 显示“创建时间、最后活动、到期时间、撤销状态”，避免含糊的自造术语。
- 当前管理员撤销自己的会话后立即回到登录流程。

### 4.8 权限诊断

- 选择主体、范围、资源和操作，查看 IAM 返回的授权结论与可解释依据。
- 诊断只读，不提供绕过授权或直接写入权限的入口。
- 输入变化后旧结论立即失效，禁止把历史结果作为新的授权依据。

### 4.9 审计

- 按事件类型、Actor、目标、Organization、Site、Command、Request 和时间范围筛选。
- 使用游标分页，详情以结构化分组呈现，不直接倾倒 JSON。
- 支持从用户、组织、Site、成员和会话工作区带筛选条件跳转。
- 不渲染 Token、凭证、私钥或未列入契约白名单的敏感元数据。

## 5. 信息架构

```text
工作台

身份与租户
- 用户
- 组织
- Site

访问控制
- 角色与权限
- 权限诊断

安全与审计
- 会话
- 审计日志
```

成员不注册为孤立的顶层 Demo 页面，而是进入 Organization 或 Site 详情工作区；用户详情可展示
其关联关系并跳转到权威范围。导航项只有在对应页面、契约、权限和测试同时存在时才启用。

## 6. 统一交互要求

- 列表筛选、排序、分页、选中 Tab 和范围选择写入 URL，刷新与浏览器前进后退可恢复。
- 每个数据页具有初始加载、刷新、空数据、筛选为空、失败、403、404、部分数据和已删除状态。
- 表格在桌面优先支持扫描和批量任务；详情、编辑和确认使用 Dialog 或 Sheet，不把所有内容铺开。
- 命令提交期间锁定重复操作；失败保留输入；成功仅在 API 确认并重新读取权威状态后显示。
- 危险操作使用明确动词、影响摘要、原因输入和焦点可恢复的确认对话框。
- 前端按稳定错误码选择字段提示、Alert、Toast、冲突刷新或权限页面，不解析 `error_message`
  决定业务逻辑。
- 使用 Lucide 图标；图标命令有可访问名称，陌生图标有 Tooltip。
- 视觉采用浅色、克制、高密度企业后台规范；不新增装饰性渐变、大圆角卡片或嵌套卡片。

## 7. 响应式与可访问性

- `>= 1280px`：固定侧栏，列表和详情可使用主从双栏。
- `768px–1279px`：可折叠侧栏，主从工作区切换为单列或 Sheet。
- `< 768px`：抽屉导航，筛选折叠，表格保留关键列，其余信息进入详情 Sheet。
- 目标视口为 `1440x1000`、`1024x768` 和 `390x844`；不得出现页面级横向滚动、重叠、
  截断、字体闪动或路由切换布局跳动。
- 导航、表格、筛选、表单、权限树、Dialog 和 Sheet 必须可使用键盘完成，焦点状态符合
  WCAG 2.2 AA。

## 8. API 与权限边界

- 页面只消费版本化 Protobuf 生成类型；契约 fixture 也必须通过同一运行时 schema。
- 浏览器调用 Admin BFF；IAM 内部地址和服务凭证不进入客户端 bundle。
- 能力投影决定菜单、路由和命令是否显示；直接路由和 Server Action 必须再次检查投影；IAM
  对最终 RPC 再次授权。
- 未提供契约的产品能力不以假数据、空白页、禁用按钮或临时 HTTP 接口占位。
- IAM 暂不因 Admin 重建而修改。缺失契约记录到 API 矩阵，待前端规格冻结后独立评审。

## 9. 非目标

- 不恢复旧 Ant Design、ProComponents、旧 Admin 页面、旧样式或兼容路径。
- 不引入第二认证权威或假认证状态。
- 不发布示例业务、示例账号或假统计。
- 不在 Admin 中实现 IAM 的生命周期、幂等、租户隔离或授权规则。
- 不在当前前端重建阶段修改 IAM 数据库、RPC 或部署方式。
- 不加入 Docker、TLS、网关或生产运维设计。

## 10. 发布验收

只有同时满足以下条件才可将 Admin 标记为 `ACCEPTED`：

1. 页面矩阵中的全部 P0 页面和状态均有真实实现，没有 Demo、Mock 或兼容分支。
2. 页面操作、能力投影、Server Action 与 API 契约逐项可追踪。
3. 单元、组件、契约、路由权限、类型、Lint、生产构建、性能和首屏样式门禁全部通过。
4. 三个目标视口均通过视觉、键盘和响应式检查。
5. 使用 fresh fixture 在可见内置浏览器完成两轮全业务 E2E，零跳过业务步骤。
6. 测试报告记录分类、整体状态、本地与 UTC 时间、逐步截图、RPC、SQL 和日志断言。
